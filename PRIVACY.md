# Privacy

## Learning cards (0.8+)

TTC displays Codex-authored explanations matched to recorded edits in the original chat. Existing public prose is eligible as labelled context only when it names the exact file and immediately precedes its edit in the same turn inside a registered worktree. The optional **⋯ → Ask this chat for a code explanation…** opens a request review without sending. Confirming **Send to this chat** sends one bounded explanation prompt to that existing chat through the official `codex queue` command, retaining its original owner, model and permissions. The command may resume that original chat on the shared Codex server. No message is sent on startup, selection, refresh or notifications. TTC makes no direct model request and creates no separate agent.

The learner payload contains bounded task metadata and one verified card, not the transcript, tool activity, branch inventory or operational replies. The explanation appears immediately, without answer selection. Legacy question/choice/answer fields are discarded. Cards are not written to a separate conversation or learning database.

A removed worktree can supply a historical comparison only when its recorded absolute path and patch match the card. This uses existing chat data and immutable virtual documents; it does not access that worktree’s current filesystem. The explanation is Codex-authored content, not proof that behavior was executed or that understanding was measured.


Type the Change has no application backend, analytics, advertising, or telemetry of its own.

## Existing Codex chats (0.7+)

TTC reads existing chats through the installed Codex app-server protocol. It first attempts a connection to an existing shared server; otherwise it starts only a local history-query transport. Its request allowlist contains initialization and thread list/read/turn/item/loaded-list operations. The read connection never starts, resumes, forks, steers or interrupts a thread. The separate explicit explanation action described above uses Codex’s own message queue. TTC never chooses a model, logs in, reads credential files or stores Codex tokens. Codex remains the owner of conversations, long-term memory, work and provider access. There is no direct OpenAI API request in the extension bundle.

Displayed chat records and source snapshots are bounded and held in memory, not persisted as another conversation database or semantic memory. Only the selected chat ID and UI/check preferences are kept in VS Code state. The source of history remains Codex. Reasoning payloads and raw tool output are excluded from the display. TTC does not scrape Codex databases or rollout file formats. It does not infer live execution from a saved interrupted/not-loaded record.

Optional live notifications use Codex's official hooks after the person reviews the configuration and trusts its exact definitions in Codex. The hook sends only a thread/turn ID, event, timestamp, working directory and tool name over a private local Unix socket to open TTC windows. It excludes prompts, responses, command contents, tool outputs and transcript paths. These notifications are retained only in memory (at most 100 current thread entries), without event history files. No notification triggers an agent action, adds context, approves a tool, blocks a turn or starts new work. The installed hook script and hook definitions persist; removing their `Type the Change: observe Codex` groups from Codex hooks settings disconnects them. Other hooks are preserved.

Old independent OAuth credentials from versions 0.2–0.5 are no longer accessed or migrated. Existing credentials and older learning journals are not silently deleted during upgrade.

## Worktrees and learning

While visible, TTC reads Git metadata for the selected chat's registered worktrees and polls the selected worktree's changes. It accepts activity-derived paths only when they belong to that inventory; multiple candidates require a choice. Other agents' changes may share that worktree, so the UI does not claim every file belongs to the selected chat. Git commands disable optional locks, external diff drivers and text conversion during comparisons. TTC creates no worktrees, commits, branches or source edits.

Selecting a file reads its last committed content and working copy, with an optional unsaved buffer from this VS Code window. Text is limited to 1 MiB per version. A temporary pair of files is removed after generating the comparison. Editor diff views use immutable in-memory documents. The practice action opens an untitled document; no edit is applied back to the worktree. Source snapshots are versioned and marked stale when later edits or commits are observed. Recorded Codex patches are labeled historical and may differ from the current file.

## Local files and MCP

The extension reads files needed for a plan and compares editor buffers. It never applies a proposed source change. The explicit **Save and Check** action saves the current editor contents of files in the review; unrelated dirty files are not saved. Comparison without a check does not save anything. Demo files are created in a temporary directory.

The optional MCP server can read bounded source files under the one workspace path you configure. The connected client chooses which files to request, so connect only a client you trust with that workspace. Its own data handling and model provider also apply. The server rejects path traversal, symlinks, protected credential paths, oversized files, and non-UTF-8 input. These checks do not guarantee that ordinary source files contain no secrets; choose the workspace accordingly.

The server writes code-containing plans to `.type-the-change/plan.json`. The extension writes dated progress metadata to `.type-the-change/status.json`. In 0.3.0 it also writes `.type-the-change/review.json`: the current session’s last 100 decision records, with your prediction, evidence, decision, step/file, buffer hash, and time. A new session replaces that journal when its first decision is recorded. Notes are not automatically sent to a model and are not included in MCP status responses. They may contain whatever private information you type; the directory should stay out of source control. A decision remains human-reported evidence. From 0.4.0, the journal may also contain separate task evidence: the selected task name, source hash, status, exit code, duration, and up to five bounded diagnostic messages. These are not sent to a model. The last chosen task fingerprint is stored in VS Code workspace state. The first check picker explicitly describes setting `task.saveBeforeRun` to `never` before it applies that workspace preference (or the user preference if no folder is open). This also affects other VS Code tasks in that scope; cancel and compare-only choices leave the preference unchanged. The extension runs a selected existing VS Code task only after an explicit action; the bundled demo has its own local check. A task can itself read files, run dependencies or use the network according to its project configuration. The extension does not capture the full terminal output or interpret an exit code as proof of correctness. These files are local, have restrictive permissions where supported, and can be removed when no session is active. Add `.type-the-change/` to the project's Git ignore rules. The MCP server has no source-editing, shell execution, or direct model-inference tools.

Your VS Code autosave, backups, synchronization, other extensions, and normal save behavior remain under your control. The extension does not upload plan history to a separate service.
